# Exercise 5 - Agent Workflow

## Goals

The goal of this exercise is to understand how to build a ReAct (Reasoning and Acting) agent using Temporal Workflows. We will combine the building blocks from previous exercises -- prompt engineering, RAG, tool calling, and MCP -- into a durable, stateful agent loop that can reason about problems, take actions, and maintain context across multiple interactions.

By the end of this exercise, you should understand:

- How the ReAct pattern maps to Temporal Workflows and Activities
- How Signals allow external systems to communicate with a running agent
- How context is maintained and compacted across potentially infinite interactions
- How Temporal provides durability, retries, and visibility for agent workloads
- How the orchestration layer and LLM layer divide responsibilities
- What patterns extend this foundation for production use

## What you need to know

### Why Temporal for AI Agents?

LLM-based agents are inherently long-running and non-deterministic. A single user query might require multiple rounds of reasoning, tool calls that depend on external APIs, and human interaction spread across minutes or hours. Traditional request-response architectures struggle with this because they have no built-in mechanism for maintaining state across those interactions, retrying failed steps, or surviving process restarts.

Temporal solves these problems by treating the entire agent loop as a durable Workflow. Here is what that gives us:

**Durability.** If the worker process crashes mid-execution -- say, between a tool call and the observation step -- Temporal replays the workflow from its event history and picks up exactly where it left off. No state is lost. This is especially important for agents that might run for hours or days.

**Automatic Retries.** When an Activity fails (an LLM API times out, a tool returns an error, a rate limit is hit), Temporal retries it according to a configurable policy. In our implementation, each Activity is configured with a maximum of 3 attempts and a 120-second timeout. You do not need to write retry logic yourself. This is especially valuable with LLMs because their output is non-deterministic -- even with structured output constraints, an LLM might occasionally return malformed JSON or an unexpected response shape. Temporal's retry mechanism acts as a safety net: if the thought activity fails to parse the LLM's response, the retry will call the LLM again with the same context, and the next attempt will very likely produce valid output.

**Signals for Human-in-the-Loop.** Temporal Signals allow external systems to send messages into a running workflow without interrupting it. Our agent uses this to receive new user messages, exit requests, and compaction triggers while the workflow is actively running. This is the foundation for building agents that can pause, wait for human input, and resume -- all without losing state.

**Visibility.** Every Activity execution, every Signal received, and every state transition is recorded in Temporal's event history. You can inspect a running or completed workflow in the [Temporal UI](http://localhost:8233) to see exactly what the agent did, what the LLM returned at each step, and where things went wrong if they did.

**Infinite Duration via Continue-As-New.** Temporal Workflows have a limit on their event history size. For agents that run indefinitely (like a persistent chat assistant), Temporal provides `continueAsNew`, which restarts the workflow with a fresh history while preserving any state you pass forward. Our agent uses this to compact its context and carry on without hitting history limits.

### The ReAct Pattern

ReAct (Reasoning and Acting) is an agent architecture where the LLM alternates between reasoning about a problem and taking actions to gather information or perform tasks. The core loop looks like this:

```
IDLE -- waiting for a user message
  |
  v
THINKING -- the LLM analyzes the query and all previous context,
            then decides: provide a final answer, or call a tool?
  |
  +-- answer --> add to context, return to IDLE
  |
  +-- action --> move to ACTING
                   |
                   v
                 ACTING -- execute the chosen tool
                   |
                   v
                 OBSERVING -- the LLM summarizes the tool's output
                   |
                   v
                 back to THINKING (loop continues)
```

Each iteration adds to the context: thoughts, actions, and observations are all recorded so the LLM can reference them in subsequent reasoning steps. The agent keeps looping until the LLM decides it has enough information to provide a final answer.

This is fundamentally different from a single LLM call. In a simple prompt-response model, you send one request and get one response. In ReAct, the LLM is part of a loop where it can iteratively refine its understanding by interacting with external tools and building up context over multiple steps.

### Division of Responsibilities

A key architectural insight is that the Temporal Workflow and the LLM layer have clearly separated responsibilities.

Temporal owns the **orchestration** -- it decides _what_ happens next in the agent loop. It manages the state machine transitions (IDLE to THINKING to ACTING to OBSERVING and back), enforces ordering, handles retries, and ensures durability. The workflow code never calls the LLM directly. It delegates every external interaction to an Activity and makes control flow decisions based on the structured responses those Activities return.

The LLM layer owns the **reasoning** -- it decides _how_ to answer. Given the accumulated context, the LLM chooses whether to call a tool or provide a final answer, generates the tool parameters, and summarizes observations. It has no knowledge of Temporal, retries, or state persistence. It simply receives context and returns a structured response.

This separation means you can swap out the LLM provider, change the prompt strategy, or add entirely new reasoning patterns without touching the workflow orchestration. Conversely, you can migrate from one orchestration framework to another without rewriting your LLM interaction logic. In our implementation, this boundary is the Activities interface: the workflow calls Activities, and the Activities call the LLM.

### How it works

The implementation is split into two layers: the Workflow (orchestration logic) and the Activities (the actual work).

#### Workflow Interface

The `AgentWorkflow` interface defines the contract for our agent. It has one main method and three Signals:

```java
@WorkflowInterface()
public interface AgentWorkflow {
    @WorkflowMethod(name = "agentWorkflow")
    WorkflowResult execute(WorkflowInput input);

    @SignalMethod(name = "message")
    void receiveMessage(MessagePayload payload);

    @SignalMethod(name = "exit")
    void requestExit();

    @SignalMethod(name = "continueAsNew")
    void requestContinueAsNew();
}
```

`execute` is the entry point. It starts the main event loop and runs until an exit is requested. It accepts a `WorkflowInput` which optionally contains state from a previous run (for continue-as-new scenarios).

`receiveMessage` allows external clients to send user messages into the running workflow. Each message includes the user's name, their message text, and a timestamp.

`requestExit` tells the agent to shut down gracefully. The workflow aggregates all token usage metrics and returns them as part of the `WorkflowResult`.

`requestContinueAsNew` triggers context compaction -- summarizing the conversation history and restarting the workflow with a smaller context via `continueAsNew`.

#### Workflow State

The workflow maintains several pieces of state that persist across the entire lifecycle of the agent:

```java
// Signal state -- populated by incoming Signals
private List<MessagePayload> pendingMsgs = new ArrayList<>();
private boolean userRequestedExit = false;
private boolean userRequestedCompaction = false;

// ReAct loop state
private ReactStep reactStep = ReactStep.IDLE;
```

`ReactStep` is an enum with four values: `IDLE`, `THINKING`, `ACTING`, and `OBSERVING`. This tracks where the agent is in the ReAct loop at any point in time.

The workflow also maintains two lists as local variables within the `execute` method: `context` (the full conversation and reasoning history as a list of XML-formatted strings) and `usage` (accumulated token counts from all LLM calls).

#### The Main Event Loop

The workflow's `execute` method implements the main event loop. Here is the simplified flow:

```
1. Initialize context and usage from input (or empty if first run)
2. Wait for a message, exit request, or compaction request
3. Enter the main loop:
   a. If exit requested --> aggregate usage, return result
   b. If compaction needed --> compact context, continueAsNew
   c. If messages pending and IDLE --> drain messages into context, set THINKING
   d. If THINKING --> call thoughtActivity
      - If answer --> add to context, persist, set IDLE
      - If action --> add thought + action to context, set ACTING
        - Call actionActivity, set OBSERVING
        - Call observationActivity, add observation to context
        - Set THINKING, continue loop
   e. Wait for next message, exit, or compaction request
```

The `Workflow.await()` calls are where Temporal's durability matters most. When the agent is idle and waiting for a message, the worker process can be shut down and restarted -- Temporal will replay the workflow and land back at the same await condition, ready to receive the next Signal.

#### Context Formatting

All entries in the context list use XML-like tags so the LLM can distinguish between different types of information:

```xml
<user_message name="Mark" date="2025-01-15">What is the weather in Austin?</user_message>
<thought>I need to check the weather. I'll use the brave_search tool.</thought>
<action><reason>Search for current weather</reason><name>brave_search</name><input>{"q":"weather Austin TX"}</input></action>
<observation>Current weather in Austin is 72F and sunny.</observation>
<answer>The current weather in Austin, TX is 72 degrees and sunny.</answer>
```

This structured format helps the LLM understand the history of its own reasoning and actions, which is critical for making good decisions in subsequent iterations.

#### Activities Interface

The Activities represent the individual units of work that the agent performs. Each Activity runs outside of the workflow's deterministic execution, which means it can make network calls, access databases, and interact with external APIs.

```java
@ActivityInterface
public interface Activities {
    ThoughtResponse thoughtActivity(List<String> context);
    String actionActivity(String toolName, ActionInput input);
    ObservationResponse observationActivity(List<String> context, String actionResult);
    CompactResponse compactActivity(List<String> context);
    void persistActivity(List<PersistMessage> messages);
}
```

Each Activity is configured with a 120-second timeout and up to 3 retry attempts:

```java
private final ActivityOptions defaultActivityOptions = ActivityOptions
    .newBuilder()
    .setStartToCloseTimeout(Duration.ofSeconds(120))
    .setRetryOptions(RetryOptions.newBuilder().setMaximumAttempts(3).build())
    .build();
```

If an LLM call times out or a tool execution fails, Temporal will automatically retry the Activity up to the configured maximum. This is especially useful for LLM API calls which can occasionally be slow or return transient errors.

#### Thought Activity

The thought activity is the core decision-making step. It sends the full context to the LLM along with a system prompt that instructs it to either provide a final answer or choose a tool to call.

The system prompt includes the list of available tools formatted as XML (from `ToolRegistry.getToolsAsXmlString()`), so the LLM knows exactly what actions it can take and what parameters each tool expects. The prompt also includes the current date (since the LLM's training data has a cutoff) and all previous steps in the ReAct loop.

The LLM responds with JSON in one of two formats:

When it wants to call a tool:

```json
{
  "thought": "I need to search for the current weather in Austin",
  "action": {
    "name": "brave_search",
    "reason": "Search for current weather data",
    "input": { "q": "weather Austin TX" }
  }
}
```

When it has enough information to answer:

```json
{
  "thought": "I now have the weather data from my search",
  "answer": "The current weather in Austin, TX is 72 degrees and sunny."
}
```

The thought activity uses the high-quality model (`AWS_MODEL_ID` from config) because this is where the most important reasoning happens. The quality of this step directly affects whether the agent picks the right tool, asks the right questions, and produces useful answers.

#### Action Activity

The action activity executes a tool by name. It looks up the tool in the `ToolRegistry`, validates that it exists, passes in the parameters, and returns the raw result.

If the tool is not found, it returns a JSON error object rather than throwing an exception. This allows the LLM to see the error in the next observation step and recover -- for example, by choosing a different tool or reformulating its approach.

The currently registered tools are:

- `brave_search` - Searches the internet using the Brave Search API. Accepts a query string (`q`) and an optional result count.
- `fetch_webpage` - Fetches the raw HTML content of a URL via HTTP GET. Accepts a `url` parameter.

Tools are registered in the `ToolRegistry` class, which maintains a map of tool names to executor functions. Each tool provides both a Bedrock-compatible `ToolSpecification` (with JSON Schema for input parameters) and an `execute` method. Adding a new tool to the agent means implementing these two things and registering it in the `ToolRegistry`.

#### Observation Activity

The observation activity takes the raw output from a tool call and asks the LLM to summarize it into a concise observation. This serves two purposes: it extracts the relevant information from what might be a large or noisy tool response, and it formats the result in a way that is useful for the next thinking step.

The observation activity uses a lower-cost model (`AWS_LOW_MODEL_ID`) because this task is straightforward summarization -- it does not require the same level of reasoning as the thought step. This is a practical cost optimization: you use the best model where reasoning quality matters and a cheaper model where it does not.

#### Compact Activity

The compact activity summarizes the entire context history into a shorter representation. This is triggered either manually (via the `compact` Signal) or automatically when Temporal suggests that the workflow should continue-as-new (because the event history is getting large).

The compaction process works like this:

1. The full context is sent to the LLM with instructions to summarize while preserving the most important information.
2. The LLM returns a compressed summary.
3. The workflow builds a new context consisting of the summary plus the last 3 entries from the original context (to preserve the most recent state).
4. The workflow calls `continueAsNew` with this compacted context, the accumulated usage metrics, and any pending messages.

The result is a fresh workflow execution that has the essential history without carrying the full weight of every previous step. This is what enables the agent to run indefinitely.

#### Persist Activity

The persist activity records user and assistant messages to an external store. In the current implementation this logs to the console, but it is designed to be extended with a database or message queue for production use. This activity runs alongside the ReAct loop -- it is called when user messages arrive and when the agent produces a final answer.

### Putting It All Together

The full lifecycle of a single user interaction looks like this:

1. An external client starts the workflow (or it is already running from a previous interaction).
2. The client sends a `message` Signal with the user's query.
3. The workflow wakes up, drains the pending message into context, and transitions to `THINKING`.
4. The thought activity analyzes the context and decides to call `brave_search`.
5. The workflow transitions to `ACTING` and executes the search tool.
6. The workflow transitions to `OBSERVING` and summarizes the search results.
7. The workflow loops back to `THINKING`. The thought activity now has the search results in context and decides it has enough information.
8. The thought activity returns an answer. The workflow adds it to context, persists it, and transitions back to `IDLE`.
9. The workflow waits for the next message.

Each of those steps is recorded in Temporal's event history. If the worker crashes at step 6, Temporal replays steps 1-5 from history and re-executes step 6 onward. The user never knows anything went wrong.

### Token Usage Tracking

Every Activity that calls the LLM returns a `UsageMetadata` record containing `inputTokens`, `outputTokens`, and `totalTokens`. The workflow accumulates these across all Activity executions and returns the aggregate when the workflow exits. This gives you visibility into the total cost of a conversation, which is important for budgeting and optimizing your agent's behavior.

### Taking It Further

The workshop implementation covers the core patterns, but a production agent workflow would likely incorporate several additional capabilities. This section describes patterns that extend the base architecture for real-world use.

#### Signal With Start

In our workshop code, starting the workflow and sending the first message are two separate operations: you start the workflow, then send a Signal. This creates a race condition -- what if the Signal arrives before the workflow is ready to receive it? Or what if you are not sure whether the workflow is already running?

Temporal solves this with `signalWithStart`, which atomically starts a workflow (if it is not already running) and delivers a Signal to it in a single operation. This is the pattern you would use in a production chat application where each user conversation maps to a single long-running workflow:

```typescript
// TypeScript example using signalWithStart
await client.workflow.signalWithStart(agentWorkflow, {
  taskQueue: "agent-task-queue",
  workflowId: workflowId,
  args: [{}],
  signal: agentWorkflowMessageSignal,
  signalArgs: [message, author, new Date().toISOString()],
});
```

In Java, the equivalent uses `SignalWithStartBatchRequest` or the `newSignalWithStartRequest` pattern on the workflow client. The key idea is the same: you never need to check whether the workflow is running before sending a message. If it is running, the Signal is delivered. If it is not, it starts and receives the Signal.

#### Per-Activity Timeout Configuration

Our workshop uses a single timeout configuration for all Activities (120 seconds, 3 retries). In practice, different Activities have very different performance characteristics and should be configured accordingly:

```typescript
// Fast, lightweight operations -- short timeouts
const { persistUserMessage, persistAgentMessage } = proxyActivities({
  startToCloseTimeout: "15 seconds",
  retry: { maximumAttempts: 5 },
});

// The thought activity calls a high-quality LLM that may take time to reason
const { thought, action } = proxyActivities({
  startToCloseTimeout: "5 minutes",
  retry: { maximumAttempts: 5 },
});

// Summarization and compaction use a faster model
const { compact, observation } = proxyActivities({
  startToCloseTimeout: "1 minute",
  retry: { maximumAttempts: 5 },
});
```

The thought activity benefits from a longer timeout because a complex reasoning chain with a high-quality model can take 30-60 seconds or more. The persist activity, on the other hand, should complete in milliseconds -- a 15-second timeout is generous, and a failure likely indicates a real problem. The observation and compact activities fall somewhere in between since they use a faster, cheaper model.

In Java, you would create multiple `ActivityOptions` objects and use `ActivityStub` creation with different options, or use `ActivityOptions.newBuilder()` with different configurations per Activity type.

#### Error Handling with Context Recovery

Our workshop implementation lets Temporal handle errors through its standard retry mechanism. A more resilient approach is to catch Activity failures within the workflow loop and push error information directly into the agent's context. This allows the LLM to see what went wrong and potentially recover by trying a different approach:

```typescript
while (true) {
  try {
    // ... normal ReAct loop ...
    const actionResult = await action(toolName, toolInput);
    const agentObservation = await observation({ context, actionResult });
    context.push(`<observation>\n${agentObservation}\n</observation>`);
  } catch (error: unknown) {
    if (error instanceof ActivityFailure) {
      context.push(
        `<error>\nActivityFailure: ${error.cause?.message}\n</error>`,
      );
    } else {
      context.push(
        `<error>\nUnknown Error: ${(error as Error).message}\n</error>`,
      );
    }
  }
}
```

With this pattern, if the `brave_search` tool fails because the API is down, the LLM sees `<error>ActivityFailure: Brave Search API returned 503</error>` in its context. On the next thinking step, it might decide to try `fetch_webpage` instead, or simply tell the user that the search service is temporarily unavailable. The agent degrades gracefully rather than crashing.

#### Token-Based Proactive Compaction

The workshop triggers compaction in two ways: manually via the `compact` Signal, or reactively when Temporal suggests `continueAsNew` because the event history is growing large. A more proactive approach is to count tokens after each answer and trigger compaction before the context becomes too large for the LLM's context window:

```typescript
if (agentThought.__type === "string") {
  context.push(`<answer>\n${agentThought.payload}\n</answer>`);

  // Count tokens in the current context
  const tokenCount = await tokens(context);
  const passedTokenLimit = tokenCount.tokenCount > tokenCount.tokenLimit;

  // Compact if either Temporal suggests it or we are approaching the token limit
  if (workflowInfo().continueAsNewSuggested || passedTokenLimit) {
    return compactAndContinueAsNew();
  }

  await continueCondition();
}
```

This is important because Temporal's `continueAsNewSuggested` flag is based on event history size, which is a Temporal-level concern. But the LLM has its own constraint: the context window size. A conversation might not have enough events to trigger Temporal's suggestion, but the accumulated context strings might be approaching the model's token limit. Counting tokens proactively ensures you compact before the LLM starts losing information or throwing errors due to context overflow.

The token counting itself can be a lightweight Activity that uses a tokenizer library (like `tiktoken` for OpenAI models or a similar tokenizer for your model provider) to estimate the total token count of the context array.

#### Query Handlers for State Inspection

Temporal Queries allow external systems to read the current state of a running workflow without affecting its execution. For an agent workflow, this is useful for building UIs that display the conversation history, debugging a stuck agent, or monitoring the context size:

```typescript
// Define a Query handler in the workflow
export const agentWorkflowQueryContext = defineQuery<string[]>(
  "agentWorkflowQueryContext",
);

// Inside the workflow function
setHandler(agentWorkflowQueryContext, () => {
  return context;
});
```

In Java, you would use the `@QueryMethod` annotation on the workflow interface. Unlike Signals, Queries are synchronous -- the caller sends a query and gets back a response immediately. This is useful for building a dashboard that shows the current state of every active agent, or for a debugging tool that lets you inspect what the LLM has seen so far.

#### Additional Signal Types

The workshop defines three Signals: message, exit, and compact. A production agent might support additional Signal types for richer interaction patterns:

**External context injection** allows systems other than the user to push information into the agent's context. For example, a monitoring system could signal the agent with a system alert, or a scheduled job could inject daily summary data:

```xml
<external_context date="2025-01-15" author="system">
Server CPU usage exceeded 90% for the last 15 minutes on host prod-web-03.
</external_context>
```

**External artifact signals** allow file references or structured data to be attached to the conversation without embedding the full content. The agent sees a description and a reference ID, and can use tools to fetch the full artifact if needed:

```xml
<external_artifact date="2025-01-15" mimetype="application/pdf" id="doc-12345">
<description>
Q4 2024 Financial Report - 47 pages, includes revenue breakdown by region.
</description>
</external_artifact>
```

**Context clearing** provides a way to reset the agent's conversation history without stopping the workflow. This is useful for multi-tenant systems where the same workflow instance might serve different conversation sessions over time.

These patterns all follow the same principle: Signals are the interface through which the outside world communicates with the agent, and the workflow's job is to incorporate those signals into the context that the LLM reasons about.
